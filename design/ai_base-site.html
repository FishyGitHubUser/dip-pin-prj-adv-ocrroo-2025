Nice brief — I’ll give a concise, actionable analysis of the core concepts for vision-impaired accessibility, then address common topics with concrete best practices (short code snippets where helpful), then run a final “extras” list of issues often missed. I’ll be direct and practical so you can apply this to real projects.

Core concepts (high level — the why)

  1. Perceivable — content must be available in ways people with low or no sight can perceive (screen readers, magnifiers, high-contrast, text-only).

  2. Operable — all functionality must be usable via keyboard and assistive devices (no mouse-only interactions).

  3. Understandable — content and controls must be predictable and understandable by screen readers and users (meaningful labels, simple language, clear error messages).

  4. Robust — use standard HTML and ARIA patterns so assistive tech can reliably parse the UI across browsers and AT (assistive technologies).

These map directly to WCAG’s POUR principles and drive the specifics below.

Fundamental, practical best practices

1) Use semantic HTML first (prefer native controls)

  • Use <button>, <a href>, <input>, <label>, <nav>, <main>, <header>, <footer>, <form>, <section>, <article> etc. Native semantics give built-in keyboard behavior and screen-reader cues.

  • Don’t use div or span for interactive controls unless you add the full keyboard & ARIA behavior.

Example — link and button:

html
<a href="/reports/2025" class="report-link">2025 annual report</a>
<button type="button" id="save">Save</button>

2) Heading structure & landmarks — readable outline

  • Use one <h1> per page; follow with <h2>, <h3> in logical order (no skipping levels).

  • Add ARIA landmarks when helpful: <main>, <nav>, <aside>, and role="search" etc. Screen reader users navigate by headings/landmarks.

3) Alternative text for images (meaningful alt)

  • Decorative images → alt="" (empty) and role="presentation" optional.

  • Informative images → concise descriptive alt text describing purpose, not visual appearance only. For complex images, link to or provide long descriptions.

html
<img src="chart.png" alt="Monthly active users increased from 1k to 4k between Jan and Jun.">

4) Forms: labels, instructions, and errors

  • Each form control must have a visible <label> or an accessible name (e.g., aria-label). Labels should be programmatically associated (for + id) or wrap the input.

  • Use aria-describedby for helper text and error details. Focus should move to the first erroneous field on submit and error message must be announced.

html
<label for="email">Email address</label>
<input id="email" name="email" type="email" required aria-describedby="emailHelp">
<div id="emailHelp">We'll never share your email.</div>

5) Keyboard accessibility (non-negotiable)

  • Everyone must be able to do everything with keyboard only (Tab, Shift+Tab, Enter, Space, Arrow keys where appropriate).

  • Maintain logical tab order that matches reading order. Avoid tabindex > 0 (prefer tabindex="0" and natural flow).

  • Provide visible focus styles (outline, not just color change). Don’t remove focus outlines without replacing them.

6) Focus management & dynamic content

  • When opening modals, trap focus inside the modal; set focus to the heading or first control; restore focus to the triggering element when closed.

  • For content loaded dynamically (ajax), use aria-live for announcements if content is important and not automatically focused.

html
<div role="dialog" aria-modal="true" aria-labelledby="modalTitle" tabindex="-1">
  <h2 id="modalTitle">Confirm deletion</h2>
  ...
</div>

<div aria-live="polite" id="status">Saved.</div>

7) Contrast & typography

  • WCAG AA contrast minimums: 4.5:1 for normal text, 3:1 for large text (18pt or 14pt bold). Aim for higher contrast for low vision.

  • Allow user text scaling / responsive text; ensure UI works at 200% zoom (WCAG requirement). Avoid fixed-size text that truncates.

8) Color and non-color cues

  • Never rely on color alone to convey information (errors, required fields). Use icons, patterns, or text labels in addition to color.

  • Use patterns/labels in charts (not color-only legends).

9) Accessible images and charts

  • Provide data tables or CSV download for charts. Use <figure> + <figcaption> and long description links for complex visuals.

10) ARIA: enhance — don’t replace semantics

  • ARIA supplements native semantics when needed (e.g., aria-expanded, aria-controls, aria-pressed). Rule of thumb: prefer native HTML; apply ARIA only when necessary and follow ARIA Authoring Practices.

  • Avoid role="button" on non-interactive elements without implementing full keyboard & focus behavior.

11) Multimedia: captions, transcripts, audio

  • Provide captions (closed captions) for video and transcripts for audio. For audio-only content, provide transcripts and controls to pause/stop/adjust volume and playback speed.

  • For auto-playing audio/video, provide a clear mechanism to stop or pause it.

12) Meaningful link text & skip links

  • Link text should describe destination/purpose (avoid “click here” or “read more” without context).

  • Provide a visible skip to content link at top of page (first focusable element) to bypass repeated navigation.

html
<a class="skip-link" href="#main">Skip to main content</a>
<main id="main">...</main>

13) Testing: manual + automated + user testing

  • Automated tools (axe, Lighthouse, WAVE) catch many problems but not all. Manual testing is essential.

  • Test with real assistive tech: NVDA (Windows), JAWS (Windows), VoiceOver (macOS/iOS), TalkBack (Android). Also test with magnifiers and high-contrast modes.

  • Include people with vision impairment in usability testing whenever possible.

Concrete examples of common patterns & fixes

Modal focus trap (concept)

  • Set tabindex="-1" on dialog container and call focus() after showing.

  • Add keyboard handler for Esc to close. On close, return focus to trigger.

Announcing updates

  • If content updates but focus doesn't move, use aria-live="polite" or assertive depending on urgency.

Accessible image with long description

<figure>
  <img src="complicated-diagram.png" alt="Architecture diagram overview">
  <figcaption>System architecture — see full description: <a href="/diagrams/arch-desc">Long description</a></figcaption>
</figure>

Testing checklist (quick prioritized list)

  1. Can you navigate and operate the site fully with keyboard only? (Tab order, focus visible, no traps)

  2. Are all images and controls announced meaningfully by a screen reader? (NVDA/VoiceOver)

  3. Do headings and landmarks allow sensible navigation? (Headings in order, <main>, <nav>)

  4. Do form fields have labels, helper text, and accessible error messages? (Use aria-describedby)

  5. Color contrast meets at least AA (4.5:1) for normal text; scale text to 200% works.

  6. Dynamic updates are announced or focused appropriately (aria-live, focus management).

  7. Multimedia has captions/transcripts and controls.

  8. No content is conveyed by color alone; charts have text alternatives or tables.

  9. Avoid inaccessible CAPTCHA; provide accessible alternative verification.

  10. PDFs & downloadable docs are tagged for accessibility or accompanied by an HTML alternative.

Additional issues frequently missed (the “take care of these too” list)

  • PDFs & Office docs: Many PDFs are untagged and unreadable by screen readers. Provide tagged PDFs or HTML alternatives. Ensure headings and reading order are preserved.

  • Third-party widgets: Widgets (calendars, payment forms, maps, social embeds) often lack proper semantics. Audit and replace or wrap with accessible alternatives.

  • SVG accessibility: Add <title> and <desc> and ensure role="img"/aria-labelledby when SVGs convey meaning.

  • Canvas and custom drawing: Provide fallback text descriptions or alternate content; canvas is not automatically accessible.

  • Chart accessibility: Provide underlying data tables and keyboard accessible drilldowns.

  • CAPTCHAs: ReCAPTCHA is problematic; provide accessible alternatives (email/phone verification, honeypot + challenge alternatives).

  • Reading order vs visual order: Ensure DOM order matches logical reading order. CSS visual reordering can confuse screen readers.

  • Focus order after SPA navigation: Single Page Apps must manage focus after route changes — set focus to page heading and update document title.

  • Dynamic content announcements overload: Overuse of aria-live="assertive" can be disruptive — use polite unless urgent.

  • Text spacing & line height: Ensure text spacing is adjustable (letter/word/line spacing) — people with low vision often benefit from increased spacing.

  • Language & localization: Include lang attribute (<html lang="en">) and use lang on content blocks when content language changes.

  • Avoid auto-forwarding on focus: Don’t auto-submit or auto-advance focus unexpectedly (e.g., telephone input that jumps). Let users control flow.

  • Icons without text: Icon buttons need accessible names (aria-label, visible text, or aria-labelledby).

  • Poorly labeled progress indicators: Progress bars should include accessible labels/values for screen readers.

  • No accessibility statement & feedback path: Provide an accessibility statement and a way for users to report issues; show that accessibility is maintained as part of the process.

  • Contrast of focus indicators: Focus rings need enough contrast against backgrounds to be visible to low vision users.

  • Animations & motion: Provide a “reduce motion” option; respect prefers-reduced-motion.

Common pitfalls to avoid

  • Over-relying on ARIA instead of fixing semantic HTML.

  • Removing focus outlines for design reasons without replacement.

  • Implementing role="button" on spans without keyboard handlers.

  • Relying on automated testing only.

  • Using images of text instead of selectable, scalable text.

Implementation & process recommendations (how to bake accessibility into projects)

  • Design systems: include accessible components (buttons, modals, forms) with documented keyboard and ARIA behavior.

  • Automated checks in CI: run axe, Pa11y, or lighthouse as part of the pipeline but treat them as early warnings.

  • Manual regression checklist: include keyboard tests, screen reader smoke tests, and zoom tests.

  • Include users with disabilities in acceptance testing.

  • Training: developers, QA, designers, product owners all need accessibility basics — include it in PR reviews and design reviews.

  • Accessibility statement & roadmap: publish current conformance level, known issues, and contact info for feedback.

Quick resource pointers (what to learn next)

  • WCAG 2.1 (and 2.2 where relevant) — for contrast, focus, mobile/tablet rules.

  • WAI ARIA Authoring Practices — correct ARIA use and patterns.

  • Screen reader keyboard shortcuts (NVDA, VoiceOver) for manual testing.

  • Accessibility tooling: axe, Lighthouse, NVDA, VoiceOver, WAVE.
